# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What huxdb is

huxdb is a desktop database management tool modeled on Navicat (reference for features and UI: https://www.navicat.com/en/products/navicat-for-postgresql). It is a Tauri 2 app with a React 19 + TypeScript + Vite frontend and a Rust backend.

- **v1 targets PostgreSQL only.** Other database engines come in later versions, so keep engine-specific code behind a boundary that a second engine can plug into later. Don't build multi-engine abstractions before a second engine actually needs them.
- **Built one feature at a time, in iterations.** Each iteration delivers one feature end to end, not the whole Navicat feature set. Keep changes scoped to the feature in progress.
- Database connections and queries belong in the Rust backend and are exposed to the UI through Tauri commands. The frontend never talks to a database directly.

## Project state

Built so far: saved PostgreSQL connection profiles (create / edit / delete / test), the main window shell (toolbar, sidebar, details pane), and a lazily loaded object tree in the sidebar (Connection → Databases → Schemas → Tables / Views / Materialized Views / Functions). Selecting a schema's Tables group (or a table under it) shows a Navicat-style tables list in the main pane (Name, Rows, OID, Owner, System Table, Comment) under an object toolbar with Open / Design / New / Delete / Import / Export buttons (the ones that act on a table enable with the row selection). The Views group (or a view) likewise shows a views list (Name, OID, Owner, System View, Comment) with Open / Design / New / Delete / Export buttons (no Import, as in Navicat). Other selections show the connection details. The view designer's Preview / Explain and the data editor's typed WHERE / ORDER BY and custom filter conditions run user SQL in a read-only scope, and the data editor otherwise generates its own statements from the grid's edits; only the query editor runs user SQL as typed. The main pane is tabbed: a permanent Objects tab (the lists above) plus one closable tab per open designer, data editor or query. The **table designer** (Design Table / New Table in the tables toolbar, or the right-click menu on a table or the Tables group) has Fields, Indexes, Foreign Keys, Uniques, Checks, Excludes, Triggers, Rules, Options, Comment and SQL Preview sub-tabs (the toolbar's Add / Delete buttons follow the active sub-tab); Save creates or alters the table in one transaction (a new table asks for its name first). The **view designer** (Design View / New View in the views toolbar, or the right-click menu on a view or the Views group) has Definition (an editable SQL editor with a result panel), Advanced (owner, check option, security barrier / invoker), Comment and SQL Preview sub-tabs, and a toolbar with Save, Preview (first 100 rows), Explain and Beautify SQL. The object designer is feature-complete for tables and views; materialized views have no designer yet. The **data editor** (Open Table in the tables toolbar, double-clicking a table in the list or tree, or Open Table in its right-click menu) shows a table's rows in an editable grid: edits, added rows and deleted rows stay pending (colour-coded) until Commit, Cancel drops them, and Begin Transaction holds a transaction across Commits until End Transaction → Commit / Rollback (or the Rollback button). Under the grid: Add, Delete, Commit, Cancel, Rollback, Refresh, Stop, and a pager (First / Previous / page / Next / Last, rows per page, "Rows X–Y of N"). Above the grid, a filter bar holds a Filter button, removable chips for the applied filter, typed WHERE and ORDER BY inputs, Apply and Clear. The Filter button opens a docked filter builder: conditions and bracket groups nested to any depth, each group AND or OR, each row with an enable checkbox, NOT and remove; operators are comparison, contains / begins with / ends with, null, empty, between, in-list and a custom SQL expression; edits are a draft until its Apply. Clicking a header sorts (ascending, descending, off; Shift-click stacks columns); the cell menu has Filter by Value / Filter Out Value / Is NULL / Is Not NULL, ANDed onto the filter. Filter and sort last as long as the tab; they change only while no edits are pending, and go back to the first page. Columns resize by dragging a header's right edge (double-click fits the column to its values); widths are remembered per table. The grid's font size (A− / % / A+ in its toolbar, or ⌘− / ⌘0 / ⌘+ while the grid has focus) is shared by all data tabs and remembered. Tables without a primary key open read-only. The **query editor** (New Query in the main toolbar, enabled with any tree selection) opens a SQL tab bound to the selected connection, in the selection's database and schema if it has them. Run or Cmd+Return runs the selection, or the current statement, which is highlighted; Run All or Cmd+Shift+Return runs everything. Stop, Continue on Error (otherwise a run stops at the first error), and database and schema selects are in its toolbar. Each statement that returns columns gets a read-only result tab with client-side pages (at most 10,000 rows or 64 MiB, with a banner), and Messages lists each statement's outcome, rows, time, notices and errors, with Go to Position. Typed BEGIN / COMMIT / ROLLBACK work, and an open or failed transaction shows the tab's dot and locks the selects. A completion list offers what fits the cursor's clause (Tab or Enter accepts, arrows move, Escape closes, Ctrl+Space opens it): after FROM or JOIN the database's tables, views, materialized views, schemas and the statement's CTEs; after SELECT, WHERE or ON the columns of the tables in FROM, including outer queries for a correlated subquery, ranked first; PostgreSQL keywords and types and the database's functions alongside. After a `.` it offers a schema's objects, or the columns of a table, alias, CTE or derived table, with their types where known. Names that need it insert quoted. Inside a function's parentheses a tooltip shows its overloads and marks the current argument (Escape hides it). With no list open, Tab indents. The toolbar's gear menu turns completion and upper-case keywords off, for all query tabs, and remembers it; its Update Code Completion reloads the catalog, which also reloads by itself after a run with DDL and when a designer saves. Text isn't saved yet: it's lost on close. In the tables list, Delete, Import and Export are still placeholders; in the views list, Open, Delete and Export are. A tab with unsaved edits (or, for a data or query tab, an open transaction) shows a dot; closing it asks Save / Discard / Cancel (Commit / Rollback / Cancel for a data or query tab), and closing the window with dirty tabs asks before quitting. The main toolbar has Connection, New Query, a separator, then Tables and Views: each is enabled when the tree selection is inside a schema, selects that schema's group via the explorer store's `showGroup(group)`, and shows as pressed while `isGroupSelection(selected, group)` holds.

Rust has unit tests. The frontend's pure modules have Vitest tests (`*.test.ts` beside them, `npm test`, no DOM or component tests), and `npm run build` (tsc strict) checks the rest. Both run in the release workflow's test job. No linter or formatter config beyond defaults.

## Workflow

- **Start each new feature on its own branch** named `feature/<name>` (e.g. `feature/query-editor`), created from `develop` (not `main`) before any changes are made. Finished features merge into `develop`, which can be pushed freely because only a merge into `main` starts a release build. `develop` is being introduced now; until it exists, ask before branching.
- **Don't commit.** The developer makes all commits so that every change is reviewed by a human. Leave the finished work uncommitted on the feature branch.
- **Releases:** merging a PR into `main` (normally from `develop`) runs `.github/workflows/release.yml`, which tests, builds macOS (Apple Silicon and Intel), Windows and Linux, and publishes a GitHub release last, so a failed run leaves no tag or release. A direct push doesn't release; run the workflow by hand for that. The version is major.minor from `tauri.conf.json` plus the next free patch from the `v*` tags (`.github/scripts/next-version.sh`), written into `tauri.conf.json` on the runner only. The workflow never commits, so the repo files keep their base version: to start a new minor or major, change it in `tauri.conf.json`, `package.json` and `Cargo.toml`. Builds are unsigned (macOS ad-hoc).
- **Plans and research live in `docs/`:** `docs/research/` for findings, `docs/recommendations/` for backlogs, `docs/phases/<feature>/` for iterations. See `docs/README.md`.

## Architecture

- **Frontend (`src/`)**: `App.tsx` lays out the Navicat-style shell: `Toolbar` (one big icon button per module; add buttons there as modules are built), `Sidebar` (the object tree), and the main pane (`MainArea`: a tab strip whose permanent Objects tab holds `DetailsPane`, plus designer tabs; all tabs stay mounted and are hidden when inactive). `DetailsPane` picks a view from the explorer's selected node: `objects/TablesView` or `objects/ViewsView` for the Tables / Views group or an object in it, otherwise `ConnectionDetails`. Both are thin wrappers over the generic `objects/ObjectListView` (loading, error/retry, Name column with icon, row selection synced to the tree) and `objects/ObjectToolbar`, passing a loader, extra columns and toolbar actions. Add new object lists the same way and route them in `DetailsPane`. Dialogs (`ConnectionDialog`, `ConfirmDeleteDialog`) are always mounted and render only when the store says so; each keys its inner form by connection id so its local state resets. `components/Modal.tsx` wraps a native `<dialog>` with daisyUI classes.
- **State**: Zustand stores in `src/stores/`. `stores/connections.ts` owns the connection list, the selected connection, and which dialog is open, so any component can open the editor or the delete prompt without passing props down.
- **Designer tabs**: `stores/tabs.ts` owns the open tabs, each of kind `table`, `view`, `data` or `query` (`openDesigner(kind, schemaRef, name | null)`, wrapped by `openTableDesigner` / `openViewDesigner` / `openDataEditor` / `openQuery`, focuses an already-open object; `isTabDirty` and closing dispatch to the kind's store), the close prompt (`pendingClose`, rendered by the always-mounted `ConfirmCloseDialog`), the quit prompt, and `schemaVersions` (bumped after a save so `ObjectListView` reloads). Selecting a tree node switches back to the Objects tab. Saving or deleting a connection closes its tabs. `stores/tableDesigner.ts` holds each tab's edit state keyed by tab id (`original` from the server, `edited`, and `baseline`; dirty = `edited` ≠ `baseline`), outside the components so the close prompt can save a hidden tab. `components/designer/`: `TableDesigner` (toolbar, sub-tabs, SQL Preview, new-table name prompt) and `FieldsGrid` (TanStack Table **v9**: module-level `tableFeatures`/columns, cells are small components reading the store; field properties panel below). `components/SqlEditor.tsx` wraps CodeMirror 6 with the PostgreSQL dialect, undo and the default key bindings; reuse it for SQL panes (`extensions` and `onReady` are fixed per mount). Fields can be inserted or reordered only before a table exists (PostgreSQL can't reorder columns). `components/designer/ObjectGrids.tsx` holds the Indexes / Foreign Keys / Uniques / Checks grids (one generic `ObjectGrid`, cells read their row via `useObject(kind, row)`), and `ColumnPickerDialog` picks ordered field lists (with ASC / DESC for indexes, an operator per element for excludes). Excludes and Triggers are `ObjectKind`s like the constraint tabs; trigger rows with a `definition` (constraint triggers, transition tables) are read-only except name, enabled state and comment. Rules are an `ObjectKind` too; a rule's commands are edited in `SqlEditDialog` (a `Modal` around the editable `SqlEditor`), and a rule whose definition couldn't be parsed is read-only the same way. `OptionsForm.tsx` is the Options tab (owner, tablespace, unlogged, fill factor, inherits, and PARTITION BY for a new table). Renaming a field rewrites the references to it in indexes and constraints, and deleting one removes it from them (objects left without fields are removed); `objectErrors` mirrors the backend's constraint checks. `lib/catalog.ts` caches the schema / table / column lookups behind the foreign key pickers and is invalidated when a designer saves.
- **Data editor**: `stores/dataEditor.ts` keeps each data tab's page, its `source` (columns, primary key, read-only reasons; reloaded with every page) and the pending edits: `edits` (row key → column → value), `deletes` and `inserts` (new rows with only their edited columns, keyed `new:<n>`). A loaded row's key is the JSON of its primary key values, so an edited key column still finds its row. Dirty = pending edits or `inTransaction`. Paging and Refresh are disabled while edits are pending. `spec` is the `DataSpec` the page was loaded with: `load` takes a candidate and stores it only when the page loads, so a rejected typed WHERE keeps the last good spec, rows and page (`FilterBar` keeps its text). `specLocked` (busy or pending edits) gates `toggleSort`, `addFilter`, `removeFilter`, `applyDraft`, `applyTyped` and `clearSpec`. The structured filter is a tree whose root is always a group; `lib/filterTree.ts` holds its pure helpers (nodes carry a client `id`, which serde ignores). `components/data/FilterBuilder.tsx` edits `filterDraft`, which only `applyDraft` puts into the spec, so a rejected filter stays for fixing; a draft never makes the tab dirty. The cell menu's `addFilter` ANDs its condition onto both the spec and the draft (`andWith`), and removing a chip removes the node from both. Blank means unfilled and blocks Apply, so the cell menu turns `''` into `is-empty`. A typed ORDER BY and a header sort replace each other; the typed WHERE is ANDed with the chips. `save` (the close prompt's Commit) applies pending edits and commits the transaction; closing a tab calls `session_close`, which rolls back. Loaded rows' keys are computed once per page (`rowKeys`). `components/data/`: `DataEditor` (transaction toolbar, `FilterBar`, banners, action bar, `PendingSummary`, `Pager`) and `DataGrid` (TanStack Table v9 with columns built per load). `DataGrid` subscribes only to `source` / `rows` / `rowKeys` / the new rows' keys (each `HeaderLabel` subscribes to its column's sort); each `DataRow` subscribes to its own pending values, selection, deleted and editing state and passes them to its cells through the `RowState` context, so an edit or click re-renders one row. Event handlers read the store at call time (`getState()`), not from render. `components/ToolButton.tsx` is the shared labelled toolbar button. Column widths and font size: `stores/dataGridPrefs.ts` (zustand `persist` to localStorage: `fontSize` and user-set `columnWidths` by `tableKey` → column name). `DataGrid` wraps its thead/tbody in `SavedWidthsTable` around `components/data/SizedTable.tsx` (shared with the query editor's grid), a fixed-layout `<table>` whose `<colgroup>` holds the widths, so dragging a column edge re-renders only it. Columns without a saved width get `defaultWidths` (`components/data/columnWidths.ts`: canvas-measured header and values of the first page, capped at 320 px), measured again only when the columns or the font size change; double-click fits with an 800 px cap. The table and thead carry `text-[1em]` because daisyUI's `.table` sets its own font size. Cells edit as text on double-click / Enter / F2; Set to NULL / Set to Empty String are in the right-click menu (NULL and empty string stay distinct); generated, identity ALWAYS and bytea columns are read-only.
- **Query editor (frontend)**: `stores/queryEditor.ts` keeps each query tab's text, target, `tx` (`idle` / `open` / `aborted`; dirty = not idle) and the last run's `outcomes`, keyed by tab id. `run` opens a Tauri `Channel`; statements report as they finish, and the `run-done` event, not the command's promise, ends a run, because large Channel messages can arrive after it returns (the promise only rejects when nothing ran). `components/query/`: `QueryEditor` (toolbar, selects, resizable result panel), `statementHighlight.ts` (a CodeMirror field holding statement ranges from a debounced `query_split`, mapped through edits until the next answer; `statementAt` must pick as `scanner::select` does), `sqlScope.ts` (pure, no catalog: tokens of the Lezer tree's current statement become nested `Scope`s with sources, CTEs, output and clauses; `lang-sql`'s grammar is flat, most column names are `Keyword` tokens, so a word is a name unless it's in `NOT_A_NAME`, and `tokensOf` spills an unclosed call's FROM back to the enclosing query), `catalogIndex.ts` (`Map` lookups along `searchScope`, and columns through CTEs, derived tables and stars), `completion.ts` (the sources, passed through `override` so `sql()`'s own isn't listed too, ranked by `RANK`, and a shared `Compartment` that `QueryEditor` reconfigures when `stores/queryPrefs.ts` or the catalog changes, so neither rebuilds the editor; only query tabs have completion. `catalogSource` doesn't use `lang-sql`'s `schemaCompletionSource`, because a CTE's columns can't live in its static, quadratic namespace. Quoting comes from the backend's `quote_ident`, which knows the reserved words, and `quoteIfNeeded` for names known only from the SQL), `signatureHelp.ts` (a `StateField` providing `showTooltip`), `QueryResults` (result tabs, Messages) and `ResultGrid` (a plain read-only table, because columns go by position and names can repeat; widths aren't saved). All offsets over IPC are UTF-16.
- **Completion catalog**: `stores/completionCatalog.ts` holds one catalog per (connection, database), separate from `lib/catalog.ts`, so a tab that changes database reads another entry and a late answer can't reach it; only the newest request per database may answer, and a refresh serves the old catalog until the new one arrives. `ensure` loads what's missing; `refresh` reloads only what something asked for. Runs set `catalogStale` from `changesCatalog` on an outcome (the scanner's first word: CREATE / ALTER / DROP / IMPORT, so a `DO` block or function call needs the manual refresh), and the refresh waits until the tab's transaction ends, because the catalog is read through the pool, which can't see uncommitted DDL. `schemaChanged` in `stores/tabs.ts` refreshes it for the designers. `SET search_path` typed in a tab isn't followed.
- **Object tree**: `stores/explorer.ts` plus `components/tree/`.
  - Every node is identified by a `TreeNodeRef`. `nodeKey()` turns it into a string key that is a prefix of all its descendants' keys; parts are joined with `\u001f`. Prefix matching on these keys is how a refresh or a closed connection drops a whole subtree.
  - Connection, database and schema nodes load their children from the backend on first expand. Group and object nodes are just views of the schema's data.
  - A per-key request counter discards responses that arrive after the node was refreshed or closed.
  - Selecting a tree node stores both `selectedKey` (cheap per-row highlight checks) and `selected` (the `TreeNodeRef`, which `DetailsPane` reads), and also sets the connections store's selected connection.
  - Saving or deleting a connection calls `forget(id)` to drop its tree.
  - `TreeNode.tsx` is the generic row. `ContextMenu.tsx` is the one app-wide right-click menu (`useContextMenu().open(e, items)`).
- **IPC contract**: `src/lib/api.ts` holds typed `invoke` wrappers, and `src/lib/types.ts` mirrors the Rust structs. Rust serializes with `#[serde(rename_all = "camelCase")]` (enums use kebab-case), so TS types match Rust field names converted to camelCase. When you change a Rust model, update `types.ts` too. Commands return `Result<T, String>`, so a rejected promise carries a plain string.
- **Styling**: Tailwind CSS v4 + daisyUI v5 with the `corporate` theme, configured CSS-first in `src/App.css` (there's no `tailwind.config.js`). Icons come from `lucide-react`.
- **Backend (`src-tauri/`)**: Logic lives in the library crate `huxdb_lib` (`src/lib.rs`); `main.rs` only calls `huxdb_lib::run()`. Edition 2024.
  - `connections/model.rs`: `ConnectionConfig` with `normalized()` and `validate()`. The UI repeats these checks in `ConnectionDialog.tsx` so it can show errors per field, but Rust has the final say.
  - `connections/store.rs`: `ConnectionStore` (Tauri managed state) keeps the list behind a `Mutex` and writes `connections.json` in the app config dir (macOS: `~/Library/Application Support/com.bluetarpsoftware.huxdb/`). Each save writes a temp file and renames it into place, with `0600` permissions on Unix. Passwords are stored in plain text there by deliberate decision. A file that can't be parsed is renamed to `connections.json.corrupt`, never overwritten.
  - `connections/postgres.rs`: PostgreSQL connect options (sqlx 0.9 with tokio runtime and native-tls) and Test Connection. With no Initial Database set, huxdb connects to `postgres`, as Navicat does.
  - `explorer/`: the tree's commands (`open_connection`, `close_connection`, `list_schemas`, `list_schema_objects`), the details pane's `list_tables` / `list_views`, and the query editor's `completion_catalog` (separate reads through the pool, leaving out TOAST and temp schemas, dropped and system columns, and trigger functions and those taking or returning `internal`; `quoted` is sent only when it differs from the name).
    - `sessions.rs` (`SessionManager`, managed state) keeps one lazy `PgPool` per (connection id, database), because a PostgreSQL connection can't switch databases. Saving or deleting a connection closes its pools.
    - `postgres.rs` holds the catalog queries. Names are always passed as bind parameters.
  - `designer/view.rs` + `view_postgres.rs`: the view designer (`load_view_design`, `preview_view_ddl`, `save_view_design`, `preview_view_rows`, `explain_view`). A definition change saves as `CREATE OR REPLACE VIEW … WITH (<all options>)` (it replaces the options with exactly those listed); option-only changes use `ALTER VIEW … SET / RESET`. Column changes CREATE OR REPLACE can't make fail with an error prefixed `[recreate] ` (`RECREATE_MARKER`), and the UI then offers a drop and re-create (DROP + CREATE + owner + comment in one transaction, no CASCADE, so dependent views make it fail safely). Preview and Explain run the unsaved definition in a `READ ONLY` transaction with a 30 s `statement_timeout` that is always rolled back; Preview finds the column names by preparing `SELECT * FROM (<def>) q`, casts every column to text and fetches 101 rows to know whether it truncated. `designer/postgres.rs::execute_all` is the shared one-transaction runner for both designers. Frontend: `stores/viewDesigner.ts` and `components/designer/ViewDesigner.tsx`; `NameDialog` is shared with the table designer; Beautify loads `sql-formatter` on demand (dynamic import keeps it out of the main bundle).
  - `designer/`: the table designer's commands (`load_table_design`, `preview_table_ddl`, `save_table_design`, and the picker lookups `list_table_columns`, `list_roles`, `list_tablespaces`, `list_trigger_functions`).
    - `model.rs`: `TableDesign` / `ColumnDesign` with `normalized()` and `validate()` (repeated in `stores/tableDesigner.ts` as `columnErrors` for per-cell errors). Each column carries `original_name` (None = new), so a name edit becomes `RENAME COLUMN`, never drop + add.
    - `postgres.rs`: `load_table_design` (pg_attribute / pg_attrdef / pg_constraint; needs PostgreSQL 12+), typmod decoding, and `generate_table_ddl(original, edited)`, a pure function emitting one statement per change in a fixed order (drop changed or removed indexes and constraints, drop changed PK, drop columns, renames, alters, add columns, add PK, rename kept objects, create new or changed ones as uniques → checks → indexes → foreign keys, comments). Identifiers are always quoted. Preview and Save use the same generator, so the preview is exactly what runs; `save_table_design` runs it in one transaction and reports the failing statement. A type change emits plain `ALTER COLUMN … TYPE` (no `USING`). Tables are not renamed from the designer. Indexes and constraints are diffed by definition: each is rendered without its name, the original's column names mapped through the edit's renames, so one whose definition didn't change is kept (PostgreSQL follows column renames) or only renamed, and any other is dropped and re-created (comments are re-applied). Indexes that back a primary key, unique or exclusion constraint are not listed as indexes; operator classes, collations, NULLS ordering and INCLUDE columns aren't modeled and are lost if such an index is edited. Exclusion constraints are a constraint kind like the others (keys from the backing index, operators from `conexclop`). Triggers are diffed the same way on their definition: changed ones are dropped first and created last (there's no CREATE OR REPLACE TRIGGER before PG 14), kept ones are renamed / re-enabled in place, and re-created ones get their enabled state and comment back; PostgreSQL's internal foreign key triggers are skipped, and the WHEN text is parsed from `pg_get_triggerdef`. Options: new tables get UNLOGGED / INHERITS / PARTITION BY / WITH (fillfactor) / TABLESPACE in CREATE TABLE plus OWNER TO; existing tables get NO INHERIT before column drops, INHERIT after column adds, and storage / owner changes at the end, with statements that rewrite the table (SET LOGGED / UNLOGGED, SET TABLESPACE) prefixed by a `-- Rewrites the whole table…` comment so SQL Preview warns. Rules (INSERT / UPDATE / DELETE only; ON SELECT would make the table a view) follow the trigger pattern: condition and actions are parsed out of the non-pretty `pg_get_ruledef` text (`parse_rule`; unparseable rules keep their full `definition` and are read-only), changed or removed rules are dropped first and created last after the triggers (comments re-applied), and kept ones are only renamed or re-commented. Not modeled yet: exclusion constraint tablespace / fill factor, autovacuum / TOAST settings, creating trigger functions or partitions; inherited fields aren't locked (PostgreSQL rejects editing them).
  - `query/`: the query editor. `scanner.rs` is pure: `split` finds statements as psql's lexer does (strings, dollar quotes, nested comments, parentheses, `BEGIN ATOMIC` bodies) and classifies each, `select` applies a Run's scope, `Offsets` converts between bytes and UTF-16, and `next_state` tracks the transaction, because sqlx keeps the server's status private and doesn't count a typed `BEGIN`. `session_postgres.rs` holds `QuerySession`, one per tab in `QuerySessions` (managed state, keyed by tab id): its own `PgConnection`, outside the pool, opened on the first Run and closed with the tab, because `SET`, temp tables and locks belong to a connection. No scopes wrap user SQL, so a failed statement aborts the user's transaction, as in psql. Statements run one at a time through `raw_sql` (text format, so no per-type decoding, and `VACUUM` works) and **a statement's stream is always read to its end**, because a dropped stream leaves its error waiting for the next statement. Past the limits, rows are discarded; only a plain read outside a transaction is cancelled there, since a cancel would abort a transaction or undo a write. A result with no rows gets its columns from `prepare`, in a savepoint inside a transaction (a failed Parse would abort it), with the statement cache cleared afterwards. `COPY … STDIN/STDOUT` and `LISTEN` are refused before sending. Notices reach only `tracing`, so a `NoticeCollector` is subscribed for each statement's future. Stop is a flag checked between statements plus `pg_cancel_backend` over a short connection of its own (the pool may be full or closing). A Run that finds the connection dead reconnects, says what was lost, and runs nothing. The live tests are `#[ignore]`d and compare the tracked transaction state with the server's. Commands: `query_split / run / cancel / end / close`. Saving or deleting a connection calls `QuerySessions::close_connection`.
  - `editor/`: the data editor. `session_postgres.rs` holds `HeldSession`, one per tab in `EditorSessions` (managed state, keyed by tab id). It isn't specific to table data, but it's tied to the pool, so query tabs share only its `CANCELLED`. Begin Transaction keeps one pooled connection with a raw `BEGIN` until `end(commit)`; every operation goes through `lease(pool)` (the held connection or a pooled one, one operation at a time per tab), records the backend pid outside the async lock, and runs inside `open_scope` / `close_scope`: a `SAVEPOINT` within the user's transaction, otherwise a transaction of its own, so a failed or cancelled operation never aborts the user's transaction. Reads (page, count) use `open_read_scope`, which adds `SET TRANSACTION READ ONLY` before the scope's first query, and are always rolled back, which also ends the read-only state inside the user's transaction. Stop is `pg_cancel_backend(pid)` from another pooled connection; the cancelled call fails with `CANCELLED` ("Cancelled"), which the UI shows as a notice. A connection that may be left mid-transaction is closed (`close_on_drop`), never returned to the pool. Saving or deleting a connection calls `EditorSessions::close_connection` (rollback); closing it in the tree doesn't, as it leaves tabs open. `postgres.rs` loads the columns / primary key and whether each is `comparable` (a default btree operator class, through domains, binary coercion and the polymorphic families; json, xml, point aren't, so they can't sort or use `=`), pages with `SELECT q.col::text … FROM (SELECT * FROM t WHERE … ORDER BY … LIMIT/OFFSET) q` (the subquery keeps real types, so a typed `ORDER BY age` or `ORDER BY 1` doesn't sort text; the primary key, or tableoid and ctid without one, is always the last sort term so pages are stable), gives filtered pages a 60 s `statement_timeout` (unfiltered pages have none, so Last works on a large table), counts with a 5 s `statement_timeout` (null on timeout), and `build_statements` (pure, unit-tested) turns an `EditBatch` into deletes → updates → inserts with values bound as text and cast `$n::<format_type>`, every column checked against the freshly loaded source. `DataSpec` (`filter` as a tree, `sort`, typed `where_sql` / `order_sql`) goes through the pure `where_clause` and `order_terms`: `prune` first drops disabled nodes and groups left empty; structured columns are checked the same way and values bound the same way, but cast to `filter_type` (`format_type(base type, -1)`), because the column's own `numeric(10,2)` or `varchar(3)` would silently round or cut a typed value and a domain's CHECK would reject one; text matching is `col::text ILIKE`, with the pattern escaped in the backend; typed text and custom conditions sit between newlines (so `--` can't reach the generated SQL), the WHERE in parentheses, and the trailing primary key term makes text that ends the ORDER BY a syntax error. Page and count queries use `persistent(false)`, which also keeps them to the extended protocol's one statement. Each UPDATE / DELETE must change exactly one row or the whole batch is undone. Commands: `session_begin / end / cancel / close` and `data_fetch_page / count / apply` (the data ones take a `target: DataTarget`). The pool's `MAX_CONNECTIONS` is 8, since each open transaction holds a connection.
  - PostgreSQL-specific code lives only in the `*postgres.rs` files; future database engines get sibling modules.
- **Adding a backend command** requires touching both sides: define a `#[tauri::command]` fn in Rust, register it in `tauri::generate_handler![...]` in `lib.rs`, then `invoke` it by name from TypeScript. Arguments are passed as a camelCase JSON object and deserialized via serde.
- **Permissions**: Tauri 2 capabilities in `src-tauri/capabilities/default.json` gate plugin/API access for the `main` window. Adding a Tauri plugin means adding the crate, `.plugin(...)` in `lib.rs`, the npm package, and its permission here.
