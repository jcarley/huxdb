# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What huxdb is

huxdb is a desktop database management tool modeled on Navicat (reference for features and UI: https://www.navicat.com/en/products/navicat-for-postgresql). It is a Tauri 2 app with a React 19 + TypeScript + Vite frontend and a Rust backend.

- **v1 targets PostgreSQL only.** Other database engines come in later versions, so keep engine-specific code behind a boundary that a second engine can plug into later. Don't build multi-engine abstractions before a second engine actually needs them.
- **Built one feature at a time, in iterations.** Each iteration delivers one feature end to end, not the whole Navicat feature set. Keep changes scoped to the feature in progress.
- Database connections and queries belong in the Rust backend and are exposed to the UI through Tauri commands. The frontend never talks to a database directly.

## Project state

Built so far: saved PostgreSQL connection profiles (create / edit / delete / test), the main window shell (toolbar, sidebar, details pane), and a lazily loaded object tree in the sidebar (Connection → Databases → Schemas → Tables / Views / Materialized Views / Functions). Selecting a schema's Tables group (or a table under it) shows a Navicat-style tables list in the main pane (Name, Rows, OID, Owner, System Table, Comment) under an object toolbar with Open / Design / New / Delete / Import / Export buttons (the ones that act on a table enable with the row selection). The Views group (or a view) likewise shows a views list (Name, OID, Owner, System View, Comment) with Open / Design / New / Delete / Export buttons (no Import, as in Navicat). Other selections show the connection details. The only user SQL huxdb runs is the view designer's Preview / Explain, always read-only; the data editor generates its own statements from the grid's edits. The main pane is tabbed: a permanent Objects tab (the lists above) plus one closable tab per open designer or data editor. The **table designer** (Design Table / New Table in the tables toolbar, or the right-click menu on a table or the Tables group) has Fields, Indexes, Foreign Keys, Uniques, Checks, Excludes, Triggers, Rules, Options, Comment and SQL Preview sub-tabs (the toolbar's Add / Delete buttons follow the active sub-tab); Save creates or alters the table in one transaction (a new table asks for its name first). The **view designer** (Design View / New View in the views toolbar, or the right-click menu on a view or the Views group) has Definition (an editable SQL editor with a result panel), Advanced (owner, check option, security barrier / invoker), Comment and SQL Preview sub-tabs, and a toolbar with Save, Preview (first 100 rows), Explain and Beautify SQL. The object designer is feature-complete for tables and views; materialized views have no designer yet. The **data editor** (Open Table in the tables toolbar, double-clicking a table in the list or tree, or Open Table in its right-click menu) shows a table's rows in an editable grid: edits, added rows and deleted rows stay pending (colour-coded) until Commit, Cancel drops them, and Begin Transaction holds a transaction across Commits until End Transaction → Commit / Rollback (or the Rollback button). Under the grid: Add, Delete, Commit, Cancel, Rollback, Refresh, Stop, and a pager (First / Previous / page / Next / Last, rows per page, "Rows X–Y of N"). Columns resize by dragging a header's right edge (double-click fits the column to its values); widths are remembered per table. The grid's font size (A− / % / A+ in its toolbar, or ⌘− / ⌘0 / ⌘+ while the grid has focus) is shared by all data tabs and remembered. Tables without a primary key open read-only. In the tables list, Delete, Import and Export are still placeholders; in the views list, Open, Delete and Export are. A tab with unsaved edits (or, for a data tab, an open transaction) shows a dot; closing it asks Save / Discard / Cancel (Commit / Rollback / Cancel for a data tab), and closing the window with dirty tabs asks before quitting. The main toolbar has Connection, New Query (mocked, no-op), a separator, then Tables and Views: each is enabled when the tree selection is inside a schema, selects that schema's group via the explorer store's `showGroup(group)`, and shows as pressed while `isGroupSelection(selected, group)` holds.

Rust has unit tests; the frontend has no test framework, so `npm run build` (tsc strict) is its only check. No linter or formatter config beyond defaults.

## Workflow

- **Start each new feature on its own branch** named `feature/<name>` (e.g. `feature/query-editor`), created from `main` before any changes are made.
- **Don't commit.** The developer makes all commits so that every change is reviewed by a human. Leave the finished work uncommitted on the feature branch.
- **Plans and research live in `docs/`:** `docs/research/` for findings, `docs/recommendations/` for backlogs, `docs/phases/<feature>/` for iterations. See `docs/README.md`.

## Commands

```bash
npm install                 # install frontend deps (Tauri CLI is a devDependency)
npm run tauri dev           # run the desktop app (starts Vite on :1420 via beforeDevCommand)
npm run tauri build         # production bundle (runs `npm run build` first, outputs from ../dist)
npm run dev                 # frontend only in a browser — Tauri `invoke` calls will fail here
npm run build               # type-check (tsc) + Vite build; this is the frontend "lint" step

# Rust side (run from src-tauri/)
cargo check
cargo clippy
cargo test                  # single test: cargo test <name>
# Live-Postgres test is #[ignore]d; run it against a throwaway server:
docker run -d --rm --name huxdb-test-pg -e POSTGRES_PASSWORD=secret -p 55432:5432 postgres:17
HUXDB_TEST_PG_PORT=55432 cargo test -- --include-ignored
```

Vite uses a fixed port (1420, `strictPort`); if it is taken, `tauri dev` fails rather than picking another port.

## Architecture

- **Frontend (`src/`)**: `App.tsx` lays out the Navicat-style shell: `Toolbar` (one big icon button per module; add buttons there as modules are built), `Sidebar` (the object tree), and the main pane (`MainArea`: a tab strip whose permanent Objects tab holds `DetailsPane`, plus designer tabs; all tabs stay mounted and are hidden when inactive). `DetailsPane` picks a view from the explorer's selected node: `objects/TablesView` or `objects/ViewsView` for the Tables / Views group or an object in it, otherwise `ConnectionDetails`. Both are thin wrappers over the generic `objects/ObjectListView` (loading, error/retry, Name column with icon, row selection synced to the tree) and `objects/ObjectToolbar`, passing a loader, extra columns and toolbar actions. Add new object lists the same way and route them in `DetailsPane`. Dialogs (`ConnectionDialog`, `ConfirmDeleteDialog`) are always mounted and render only when the store says so; each keys its inner form by connection id so its local state resets. `components/Modal.tsx` wraps a native `<dialog>` with daisyUI classes.
- **State**: Zustand stores in `src/stores/`. `stores/connections.ts` owns the connection list, the selected connection, and which dialog is open, so any component can open the editor or the delete prompt without passing props down.
- **Designer tabs**: `stores/tabs.ts` owns the open designer tabs, each of kind `table` or `view` (`openDesigner(kind, schemaRef, name | null)`, wrapped by `openTableDesigner` / `openViewDesigner`, focuses an already-open object; `isTabDirty` and closing dispatch to the kind's store), the close prompt (`pendingClose`, rendered by the always-mounted `ConfirmCloseDialog`), the quit prompt, and `schemaVersions` (bumped after a save so `ObjectListView` reloads). Selecting a tree node switches back to the Objects tab. Saving or deleting a connection closes its tabs. `stores/tableDesigner.ts` holds each tab's edit state keyed by tab id (`original` from the server, `edited`, and `baseline`; dirty = `edited` ≠ `baseline`), outside the components so the close prompt can save a hidden tab. `components/designer/`: `TableDesigner` (toolbar, sub-tabs, SQL Preview, new-table name prompt) and `FieldsGrid` (TanStack Table **v9**: module-level `tableFeatures`/columns, cells are small components reading the store; field properties panel below). `components/SqlEditor.tsx` wraps CodeMirror 6 with the PostgreSQL dialect; reuse it for SQL panes. Fields can be inserted or reordered only before a table exists (PostgreSQL can't reorder columns). `components/designer/ObjectGrids.tsx` holds the Indexes / Foreign Keys / Uniques / Checks grids (one generic `ObjectGrid`, cells read their row via `useObject(kind, row)`), and `ColumnPickerDialog` picks ordered field lists (with ASC / DESC for indexes, an operator per element for excludes). Excludes and Triggers are `ObjectKind`s like the constraint tabs; trigger rows with a `definition` (constraint triggers, transition tables) are read-only except name, enabled state and comment. Rules are an `ObjectKind` too; a rule's commands are edited in `SqlEditDialog` (a `Modal` around the editable `SqlEditor`), and a rule whose definition couldn't be parsed is read-only the same way. `OptionsForm.tsx` is the Options tab (owner, tablespace, unlogged, fill factor, inherits, and PARTITION BY for a new table). Renaming a field rewrites the references to it in indexes and constraints, and deleting one removes it from them (objects left without fields are removed); `objectErrors` mirrors the backend's constraint checks. `lib/catalog.ts` caches the schema / table / column lookups behind the foreign key pickers and is invalidated when a designer saves.
- **Data editor**: `stores/dataEditor.ts` keeps each data tab's page, its `source` (columns, primary key, read-only reasons; reloaded with every page) and the pending edits: `edits` (row key → column → value), `deletes` and `inserts` (new rows with only their edited columns, keyed `new:<n>`). A loaded row's key is the JSON of its primary key values, so an edited key column still finds its row. Dirty = pending edits or `inTransaction`. Paging and Refresh are disabled while edits are pending. `save` (the close prompt's Commit) applies pending edits and commits the transaction; closing a tab calls `session_close`, which rolls back. Loaded rows' keys are computed once per page (`rowKeys`). `components/data/`: `DataEditor` (transaction toolbar, banners, action bar, `PendingSummary`, `Pager`) and `DataGrid` (TanStack Table v9 with columns built per load). `DataGrid` subscribes only to `source` / `rows` / `rowKeys` / the new rows' keys; each `DataRow` subscribes to its own pending values, selection, deleted and editing state and passes them to its cells through the `RowState` context, so an edit or click re-renders one row. Event handlers read the store at call time (`getState()`), not from render. `components/ToolButton.tsx` is the shared labelled toolbar button. Column widths and font size: `stores/dataGridPrefs.ts` (zustand `persist` to localStorage: `fontSize` and user-set `columnWidths` by `tableKey` → column name). `DataGrid` wraps its thead/tbody in `SizedTable`, a fixed-layout `<table>` whose `<colgroup>` holds the widths, so dragging a column edge re-renders only it. Columns without a saved width get `defaultWidths` (`components/data/columnWidths.ts`: canvas-measured header and values of the first page, capped at 320 px), measured again only when the columns or the font size change; double-click fits with an 800 px cap. The table and thead carry `text-[1em]` because daisyUI's `.table` sets its own font size. Cells edit as text on double-click / Enter / F2; Set to NULL / Set to Empty String are in the right-click menu (NULL and empty string stay distinct); generated, identity ALWAYS and bytea columns are read-only.
- **Object tree**: `stores/explorer.ts` plus `components/tree/`.
  - Every node is identified by a `TreeNodeRef`. `nodeKey()` turns it into a string key that is a prefix of all its descendants' keys; parts are joined with `\u001f`. Prefix matching on these keys is how a refresh or a closed connection drops a whole subtree.
  - Connection, database and schema nodes load their children from the backend on first expand. Group and object nodes are just views of the schema's data.
  - A per-key request counter discards responses that arrive after the node was refreshed or closed.
  - Selecting a tree node stores both `selectedKey` (cheap per-row highlight checks) and `selected` (the `TreeNodeRef`, which `DetailsPane` reads), and also sets the connections store's selected connection.
  - Saving or deleting a connection calls `forget(id)` to drop its tree.
  - `TreeNode.tsx` is the generic row. `ContextMenu.tsx` is the one app-wide right-click menu (`useContextMenu().open(e, items)`).
- **IPC contract**: `src/lib/api.ts` holds typed `invoke` wrappers, and `src/lib/types.ts` mirrors the Rust structs. Rust serializes with `#[serde(rename_all = "camelCase")]` (enums use kebab-case), so TS types match Rust field names converted to camelCase. When you change a Rust model, update `types.ts` too. Commands return `Result<T, String>`, so a rejected promise carries a plain string.
- **Styling**: Tailwind CSS v4 + daisyUI v5 with the `corporate` theme, configured CSS-first in `src/App.css` (there's no `tailwind.config.js`). Icons come from `lucide-react`.
- **Backend (`src-tauri/`)**: Logic lives in the library crate `huxdb_lib` (`src/lib.rs`); `main.rs` only calls `huxdb_lib::run()`. Edition 2024.
  - `connections/model.rs`: `ConnectionConfig` with `normalized()` and `validate()`. The UI repeats these checks in `ConnectionDialog.tsx` so it can show errors per field, but Rust has the final say.
  - `connections/store.rs`: `ConnectionStore` (Tauri managed state) keeps the list behind a `Mutex` and writes `connections.json` in the app config dir (macOS: `~/Library/Application Support/com.bluetarpsoftware.huxdb/`). Each save writes a temp file and renames it into place, with `0600` permissions on Unix. Passwords are stored in plain text there by deliberate decision. A file that can't be parsed is renamed to `connections.json.corrupt`, never overwritten.
  - `connections/postgres.rs`: PostgreSQL connect options (sqlx 0.9 with tokio runtime and native-tls) and Test Connection. With no Initial Database set, huxdb connects to `postgres`, as Navicat does.
  - `explorer/`: the tree's commands (`open_connection`, `close_connection`, `list_schemas`, `list_schema_objects`) and the details pane's `list_tables` / `list_views`.
    - `sessions.rs` (`SessionManager`, managed state) keeps one lazy `PgPool` per (connection id, database), because a PostgreSQL connection can't switch databases. Saving or deleting a connection closes its pools.
    - `postgres.rs` holds the catalog queries. Names are always passed as bind parameters.
  - `designer/view.rs` + `view_postgres.rs`: the view designer (`load_view_design`, `preview_view_ddl`, `save_view_design`, `preview_view_rows`, `explain_view`). A definition change saves as `CREATE OR REPLACE VIEW … WITH (<all options>)` (it replaces the options with exactly those listed); option-only changes use `ALTER VIEW … SET / RESET`. Column changes CREATE OR REPLACE can't make fail with an error prefixed `[recreate] ` (`RECREATE_MARKER`), and the UI then offers a drop and re-create (DROP + CREATE + owner + comment in one transaction, no CASCADE, so dependent views make it fail safely). Preview and Explain run the unsaved definition in a `READ ONLY` transaction with a 30 s `statement_timeout` that is always rolled back; Preview finds the column names by preparing `SELECT * FROM (<def>) q`, casts every column to text and fetches 101 rows to know whether it truncated. `designer/postgres.rs::execute_all` is the shared one-transaction runner for both designers. Frontend: `stores/viewDesigner.ts` and `components/designer/ViewDesigner.tsx`; `NameDialog` is shared with the table designer; Beautify loads `sql-formatter` on demand (dynamic import keeps it out of the main bundle).
  - `designer/`: the table designer's commands (`load_table_design`, `preview_table_ddl`, `save_table_design`, and the picker lookups `list_table_columns`, `list_roles`, `list_tablespaces`, `list_trigger_functions`).
    - `model.rs`: `TableDesign` / `ColumnDesign` with `normalized()` and `validate()` (repeated in `stores/tableDesigner.ts` as `columnErrors` for per-cell errors). Each column carries `original_name` (None = new), so a name edit becomes `RENAME COLUMN`, never drop + add.
    - `postgres.rs`: `load_table_design` (pg_attribute / pg_attrdef / pg_constraint; needs PostgreSQL 12+), typmod decoding, and `generate_table_ddl(original, edited)`, a pure function emitting one statement per change in a fixed order (drop changed or removed indexes and constraints, drop changed PK, drop columns, renames, alters, add columns, add PK, rename kept objects, create new or changed ones as uniques → checks → indexes → foreign keys, comments). Identifiers are always quoted. Preview and Save use the same generator, so the preview is exactly what runs; `save_table_design` runs it in one transaction and reports the failing statement. A type change emits plain `ALTER COLUMN … TYPE` (no `USING`). Tables are not renamed from the designer. Indexes and constraints are diffed by definition: each is rendered without its name, the original's column names mapped through the edit's renames, so one whose definition didn't change is kept (PostgreSQL follows column renames) or only renamed, and any other is dropped and re-created (comments are re-applied). Indexes that back a primary key, unique or exclusion constraint are not listed as indexes; operator classes, collations, NULLS ordering and INCLUDE columns aren't modeled and are lost if such an index is edited. Exclusion constraints are a constraint kind like the others (keys from the backing index, operators from `conexclop`). Triggers are diffed the same way on their definition: changed ones are dropped first and created last (there's no CREATE OR REPLACE TRIGGER before PG 14), kept ones are renamed / re-enabled in place, and re-created ones get their enabled state and comment back; PostgreSQL's internal foreign key triggers are skipped, and the WHEN text is parsed from `pg_get_triggerdef`. Options: new tables get UNLOGGED / INHERITS / PARTITION BY / WITH (fillfactor) / TABLESPACE in CREATE TABLE plus OWNER TO; existing tables get NO INHERIT before column drops, INHERIT after column adds, and storage / owner changes at the end, with statements that rewrite the table (SET LOGGED / UNLOGGED, SET TABLESPACE) prefixed by a `-- Rewrites the whole table…` comment so SQL Preview warns. Rules (INSERT / UPDATE / DELETE only; ON SELECT would make the table a view) follow the trigger pattern: condition and actions are parsed out of the non-pretty `pg_get_ruledef` text (`parse_rule`; unparseable rules keep their full `definition` and are read-only), changed or removed rules are dropped first and created last after the triggers (comments re-applied), and kept ones are only renamed or re-commented. Not modeled yet: exclusion constraint tablespace / fill factor, autovacuum / TOAST settings, creating trigger functions or partitions; inherited fields aren't locked (PostgreSQL rejects editing them).
  - `editor/`: the data editor. `session_postgres.rs` holds `HeldSession`, one per tab in `EditorSessions` (managed state, keyed by tab id) and not specific to table data, so a query editor can reuse it. Begin Transaction keeps one pooled connection with a raw `BEGIN` until `end(commit)`; every operation goes through `lease(pool)` (the held connection or a pooled one, one operation at a time per tab), records the backend pid outside the async lock, and runs inside `open_scope` / `close_scope`: a `SAVEPOINT` within the user's transaction, otherwise a transaction of its own, so a failed or cancelled operation never aborts the user's transaction. Reads (page, count) are always rolled back. Stop is `pg_cancel_backend(pid)` from another pooled connection; the cancelled call fails with `CANCELLED` ("Cancelled"), which the UI shows as a notice. A connection that may be left mid-transaction is closed (`close_on_drop`), never returned to the pool. Saving or deleting a connection calls `EditorSessions::close_connection` (rollback); closing it in the tree doesn't, as it leaves tabs open. `postgres.rs` loads the columns / primary key, pages with `SELECT col::text … ORDER BY <table-qualified primary key, or ctid without one> LIMIT/OFFSET` (a bare name would sort by the text output column), counts with a 5 s `statement_timeout` (null on timeout), and `build_statements` (pure, unit-tested) turns an `EditBatch` into deletes → updates → inserts with values bound as text and cast `$n::<format_type>`, every column checked against the freshly loaded source. Each UPDATE / DELETE must change exactly one row or the whole batch is undone. Commands: `session_begin / end / cancel / close` and `data_fetch_page / count / apply` (the data ones take a `target: DataTarget`). The pool's `MAX_CONNECTIONS` is 8, since each open transaction holds a connection.
  - PostgreSQL-specific code lives only in the `*postgres.rs` files; future database engines get sibling modules.
- **Adding a backend command** requires touching both sides: define a `#[tauri::command]` fn in Rust, register it in `tauri::generate_handler![...]` in `lib.rs`, then `invoke` it by name from TypeScript. Arguments are passed as a camelCase JSON object and deserialized via serde.
- **Permissions**: Tauri 2 capabilities in `src-tauri/capabilities/default.json` gate plugin/API access for the `main` window. Adding a Tauri plugin means adding the crate, `.plugin(...)` in `lib.rs`, the npm package, and its permission here.
- App identifier: `com.bluetarpsoftware.huxdb`. CSP is currently disabled (`"csp": null` in `tauri.conf.json`).
